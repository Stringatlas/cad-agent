# Provider-backed scene chat

[Task019](tasks/019-model-chat-loop.md) connects Scene chat to the server's explicitly configured OpenAI API-key or ChatGPT-plan provider. Credentials remain server-side; there is no paid-key fallback. This is a read-only, structured-scene chat loop—not autonomous CAD or the complete VLM harness.

## Use it

1. Configure **`apps/server/.env`** as described in [provider authentication](provider-auth.md), then restart your local backend after configuration/source changes. Imported test factories still default to disabled authentication. No keys belong in the web environment or browser.
2. Open **http://127.0.0.1:5173**. For ChatGPT, use **Account → Continue with ChatGPT**, complete **Continue with ChatGPT** in the backend tab, then return. Account status checks again on return; **Refresh status** is also available. Identity-only sign-in is insufficient; plan-usage permission is required. The header distinguishes connected/disconnected/unavailable states; the enabled-plan card links to official [Manage usage](https://chatgpt.com/settings/usage), not API billing.
3. Scene chat discovers models automatically and selects the first available model in provider order. A still-valid choice survives catalog refresh and tab changes; **Refresh models** remains available for manual recovery. Catalog discovery contacts the configured provider, but does not generate an answer. Authentication readiness or a listed model does not prove successful inference or model compatibility. The API-key catalog can include models unsuitable for Responses/function calling; select a compatible model. ChatGPT choices come from the selected account's visible catalog.
4. Cmd/Ctrl-click scene points to append **Point 1**, **Point 2**, and more; and/or select a synthetic entity. Remove individual references in **Scene references**, inspect **Current model context**, type your request, and **Send**. Sending makes a real provider request and may consume plan usage or incur API charges. No inference request is sent automatically, and failures are never automatically retried.
5. Text streams incrementally. Only a complete provider response and validated stream ending mark the answer complete. **Cancel** preserves an explicitly incomplete partial; the next Send starts a fresh server conversation. **New chat** clears local history while preserving your draft.

Idle selections, area and revision changes within the same mode/project session/frame preserve completed history; each send binds fresh scene context. Changed mode/project-session/frame, model or account disconnects continuation and suppresses stale responses. No displayed transcript is replayed by the client: the server sends earlier completed user, assistant and tool items to the provider. Returning focus/visibility revalidates the catalog; unchanged generation/model preserves continuation, including an active stream. Temporary catalog transport/validation failure blocks Send until revalidated without discarding history. A validated terminal server error plus clean EOF retains the last successful checkpoint (except stale account/conversation/model errors); the failed turn is display-only, never automatically retried. Cancellation, timeout and ambiguous/malformed transport still drop continuation, with a visible interruption notice. Draft, displayed history and model choice stay in the mounted workspace across scene/browser tab changes, not browser storage; reloading/closing the workspace clears them. No credentials are persisted in the browser.

The ChatGPT account presentation follows the official [SIWC UI/UX](https://developers.openai.com/siwc/ui-ux-guidelines) and [button assets](https://developers.openai.com/siwc/website). A persistent plan-enabled confirmation replaces a first-ever-sign-in welcome modal: the sanitized local status deliberately has no account identity or first-login persistence. It does not show invented usage, identity or provider inference success. See [Task024](tasks/024-workspace-chat-qol.md) for bounded acceptance and fixture browser evidence.

## Actual model request inspector

Each assistant message has **Actual model requests** with an expandable entry per provider round (up to 17). This is a safe projection of the same effective body used for dispatch: actual `instructions`, input roles/text, scene provenance, visible replayed history, tool definitions/calls/results, model and mode-specific options. It is not a reconstruction of the provider's internal prompt, and no system-role message is invented. Continued turns show the server's actual replay, not a browser transcript upload.

Snapshots start **prepared**, then **dispatched** when dispatch is invoked (not proof of receipt), then **completed**, **failed** or **cancelled** as reported by the server. Round completion means the server validated that provider response and EOF, not that the whole chat turn or a geometry operation succeeded. On local cancellation/context change/disconnection, unfinished monitoring is labelled separately: provider completion/cancellation cannot be confirmed. The continuation notice distinguishes an active server handle from display-only retained messages.

The inspector excludes credentials/authentication headers and opaque reasoning, with explicit omission markers; unknown fields and truncation are labelled too. It is not a general secret scrubber of user-authored text: text you deliberately send is visible. Each snapshot is capped at 48 KiB with at most 128 input items and 12,000 characters per text field; the browser retains at most 256 KiB of snapshots, evicting oldest entries with visible counts independently of answer text. No request log or browser storage is added. **New chat**, workspace reload or closing clears this local inspection history. See [Task025](tasks/025-model-request-inspector.md) for fixture-only verification and limits.

## Scene context and authority

[Task026](tasks/026-numbered-scene-points.md) replaces A/B targets with append-only numbered points in Toronto and the synthetic demo. Each successful pick adds a distinct reference, including repeated picks of the same record. All active references enter context; hidden-source points do not. The list and markers support individual removal. At 32 retained references, further picks are explicitly rejected without replacing earlier ones. Numbers are allocated by the mounted workspace: removal, clear, source/artifact/project resets never reuse them; rejected attempts may leave gaps. Reload starts a new sequence at 1, with no browser persistence. Coincident labels can overlap; the list distinguishes every retained reference.

- Synthetic selections pass through the authoritative project's exact entity/point, session, geometry revision, meter and frame checks. Selected box parameters and exact original numbered point references reach the model.
- Toronto attachments retain names, original binary64 coordinates, dataset artifact revision, source file/row, meter units, right-handed Z-up frame and translation-only origin. The server checks artifact revision, source-row admission and metadata bounds. It **does not independently reread/verify the exact original point record** at this chat boundary; the model receives `recordValidation: unverified`, not fabricated geometric evidence.
- Toronto is **unmapped to the synthetic project**. Non-demo modes may carry an empty project revision binding but never hidden synthetic selections. A missing project authority does not silently seed substitute geometry.
- No screenshot/image, point-cloud observation download, nearest-label query or CAD body is automatically supplied to this model loop. Existing deterministic inspection remains under Technical tools.

The default model-callable tool is the namespaced read-only **`scene.inspect_scene`**, returning the actual bound context. Explicit screenshot turns also expose **`scene.resolve_visual_pixel`**, returning original browser point provenance or a conservative no-hit/ambiguous result; these are browser observations, not independently server-verified original records. Model tools cannot approve/propose edits, create channels/CAD, Save, Load, Undo or publish geometry. Existing box parameter preview and deliberate exact approval remain separate. Model text, stream completion and rendered meshes are **not CAD verification**.

## Optional scene screenshots

In Toronto3D or Synthetic demo, select a model from the configured provider catalog and choose the **camera icon in the chat composer**, drag a crop (or enter pixel coordinates) in the modal, choose **Attach JPEG**, then **Send**. Reset whole image keeps the full view; Cancel/Escape returns to chat. A compact removable thumbnail shows the compressed dimensions and size. Nothing is uploaded by capture alone. Remove screenshot returns to text-only sending. Screenshots are observations of the captured instant, including visible CAD solids, pending ghosts, point edits and derived overlays. Camera/resize/LOD/overlay changes do not invalidate attached bytes or cancel an answer. Older captures remain usable after geometry changes; current scene/tool bindings and human approval remain independent. Switching scene modes clears the local attachment. A new capture replaces only the live pixel-grounding cache, not an already attached image.

Images are retained with their messages and replayed with prior conversation history on subsequent sends. User attachments and model-requested captures render inline in chat. Idle selection, area and revision updates keep the conversation while the next turn binds fresh scene context; account/model/workspace-session changes and ambiguous interruptions still reset continuation. Confirmed failed followups preserve earlier successful history, excluding the failed turn. Images have a separate 12 MiB encoded history budget; text/tool history remains bounded at 512 KiB and conversations at 16 turns. History is volatile, not persisted across reloads. Only the current turn's latest capture has pixel-grounding tools; older images remain historical context. See [Task051](tasks/051-chat-context-history.md). Chat prepares JPEG at quality78%, downsampled to at most1280 pixels on its longest edge without upscaling. Sent images are capped at2MiB; select a smaller crop if necessary. The original PNG stays local (up to4096 per dimension/12MiB for capture/export). Original camera/viewport/source metadata is preserved separately from the crop and output dimensions. Model pixels refer to the compressed crop and map by pixel center back to original captured drawing-buffer pixels; this is browser-observed evidence, not independent server verification. In both API-key and ChatGPT-plan modes, any model admitted by the configured provider catalog can attempt explicit image input. The catalog does not verify image capability, and the app does not infer it from model names. The provider may reject unsupported input; rejection stays an incomplete error with no automatic retry, image stripping or text-only fallback. Models absent from the catalog remain rejected before dispatch. No live compatibility claim is made by fixture tests. Task029 removes the earlier task028 name allowlist.

Model-requested `scene.capture_scene` accepts optional `colorMode: "rgb" | "type"` for any current/top-down/explicit-camera view. Toronto captures use natural RGB or semantic point-type colors across source overview/adaptive/manual detail, without changing the user's camera or display mode. Omission uses the current display mode. `coverage.pointColorMode` records the actual capture mode; type captures include a labeled `pointTypeKey`. Edit/ghost/derived-overlay styles are unchanged. Explicit color modes in unsupported viewers return unavailable; default synthetic captures remain supported. See [Task062](tasks/062-agent-capture-color-mode.md).

The pixel tool takes observationId and integer x/y in top-left image drawing-buffer pixels, not CSS coordinates. It resolves only visible displayed points while the live view still matches the capture, never the whole dataset, using one-use request/tool/observation nonce binding and a15s browser reply deadline. After navigation or scene changes it returns unavailable without cancelling the answer; no historical geometry snapshot is retained. Captures containing point edits/previews conservatively withhold original-record pixel provenance rather than describing moved pixels as original positions. Original coordinates/provenance stay explicitly browser-observed and unmapped across Toronto/synthetic frames. No CAD mutation or independent original-record verification is implied. The actual-request inspector shows image MIME/hash/byte count/dimensions, with `image-bytes` omission, never raw base64.

## Protocol and privacy

- `GET /chat/models` returns only mode/readiness/fixed code, opaque lifecycle generation and bounded model IDs/labels.
- `POST /chat/turn` accepts a bounded request identity, opaque conversation handle or null, generation, selected model, user text and explicit scene context. Clients cannot supply assistant history, credentials, provider endpoints or executable tools.
- Responses are bounded NDJSON `start`, `delta`, `tool`, per-round `request-inspection`/`request-phase` and exactly one `done`/`error` event. The client validates identity, terminal framing and EOF; a transport failure never becomes a completed answer.
- The server uses only public `https://api.openai.com/v1/models` and `/responses`, rejecting redirects. Provider SSE parsing preserves complete output items, including completed-item encrypted reasoning and assistant phase, for stateless replay. Opaque reasoning stays server-side, not in visible chat/tool context. Missing/empty Content-Type enters the same strict SSE parser, not a JSON fallback; explicit incompatible media types still reject. A successful `response.completed` with explicit `output: []` can retain fully finalized `output_item.done` snapshots in contiguous wire-index order. Unfinished observed items, gaps, conflicts and nonempty partial terminal arrays still reject. This is an app compatibility policy: official SDKs allow empty terminal output but do not themselves reconstruct an explicitly empty array. Completion **and EOF** remain required before tool dispatch/history commitment.
- ChatGPT requests use `stream:true`, `store:false`, full input arrays, instructions/developer context and namespaced function tools. They omit HTTP `previous_response_id`, system-role input and unsupported sampling/output-cap fields. API-key requests also use stateless streaming and add `max_output_tokens:4096`.
- Full replay history is volatile server memory; only successful turns enter it. No browser credential/history storage, project persistence or logging of provider bodies is added. Provider data handling is still subject to the configured provider's policies; `store:false` is not a claim of zero provider retention.

## Bounds and recovery

| Resource | Limit |
| --- | --- |
| User text / request | 12,000 characters / 64 KiB |
| Admission | One active catalog/turn request; 30 requests/minute |
| Provider operation | 90 seconds per round; 4 MiB total provider body per turn; 128 KiB frame |
| Answer / scene actions | 32,000 characters / 64 scene actions per turn |
| Skill discovery/loading | 16 separate calls per turn; up to 81 total provider rounds |
| Downstream browser stream | 16 MiB including bounded request-inspection snapshots |
| Conversations | Eight retained completed conversations, 30-minute idle TTL |
| Conversation | 16 completed turns; 512 KiB text/tool replay history |
| Catalog | Up to 128 models |

ChatGPT rejects provider-side `max_output_tokens`; local output/deadline cancellation is **not a guaranteed provider token-spend ceiling**. A disconnected request may already have consumed usage.

Each failed assistant message now shows its own specific failure and recovery panel, retained even after a later explicit send succeeds. Empty or partial text still remains incomplete, not committed server history.

For a parser failure, the backend terminal prints a single `[model-provider]` JSON diagnostic with a fixed parser `check` tag and HTTP status, for example `{"operation":"responses","check":"snapshot-conflict","httpStatus":200}`. A rejected non-SSE response additionally includes a closed `responseFormat` category: `json`, `html`, `text`, `missing` or `other`, with the corresponding UI code `provider-format-*`. Example: `{"operation":"responses","check":"content-type","httpStatus":200,"responseFormat":"json"}`. This classifies only the declared header; after task023, `missing` applies only to a nonempty malformed declaration with no media type, not an absent/empty header. Task022 additionally inspects at most1KiB/16reads/250ms of a wrong-MIME HTTP200 body internally, then cancels it. Closed appearance tags (`empty`, `sse-like`, `json-like`, `html-like`, `other`, `timeout`, `read-error`, `cancelled`) are not protocol validation or inference success; wrong-MIME content remains rejected unconditionally. Unknown/vendor media types fall into `other`.

For the authorized local investigation, wrong-MIME rejections also write content-redacted records under Node's OS temp directory: `spatial-model-diagnostics-*/diagnostic-<pid>-<sequence>.json`. Randomized directories are0700, exclusively created files0600, and each writer retains its latest8 records (older process directories remain until OS/operator cleanup). Schema1 records PID/local timestamp/sequence, status, closed format/body-appearance, exact-expected/absent/other URL category, allowlisted response type, redirected and body-presence flags. No raw URL, header, prefix or error text is stored; artifact failure cannot replace rejection. These backend-only records are not exposed via HTTP or chat events. Test records must not be confused with an actual listening backend PID.

Diagnostics do not log prompts, response text, opaque reasoning, raw exceptions, raw headers/IDs or credentials. Share only that diagnostic line and the UI error code—not `.env`, authentication files, request bodies or headers. They identify a rejected check, not proof of the provider's root cause. Development watchers may reload on source changes; otherwise deliberately restart/refresh to load them. No model request or retry is automatic. A missing diagnostic can mean failure outside the instrumented parser checks (for example transport/UTF-8 decoding or admission). [Task021](tasks/021-model-failure-observability.md) records the bounded fake-provider/browser verification; task023 records a successful bounded live ChatGPT-plan check after two parser compatibility fixes.

Fixed codes distinguish unavailable credentials/permission, unsupported capability/model, plan eligibility/usage, stale scene/account/conversation, resource limits and interrupted streams. Check Account, explicitly refresh models or start New chat as appropriate; do not repeatedly retry usage/policy failures. At 16 turns, start a new conversation. At eight retained conversations, New chat alone does not reclaim server history: wait for 30-minute idle expiry, or deliberately restart the local server (volatile chat history is lost). Authentication, provider availability and inference success remain distinct.
