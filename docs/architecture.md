# Architecture

## Implemented foundation

The product goal is a VLM harness that inspects point-cloud scenes and makes verified CAD edits. The current implementation is a shared-project scene/chat workspace with deterministic read-only inspection, explicit local persistence and human-approved box parameter edits, bounded Toronto3D preview, a concrete point observation boundary and an ephemeral real-kernel CAD sandbox. It is not yet the model-driven, project-integrated CAD editing loop. Pi is external development tooling, not a product runtime dependency.

| Boundary | Current responsibility |
| --- | --- |
| `packages/contracts` | Readonly TypeScript project/entity/coordinate types and runtime validation. |
| `packages/project-state` | Demo generation, entity lookup, disposable selection/local-world conversion and checked box/inverse candidates preserving unrelated entities. |
| `packages/geometry` | `GeometryAdapter.bounds` and analytic `boxBounds` for proposals; separate kernel-independent `CadAdapter` and worker-loaded actual OpenCascade implementation. |
| `packages/agent-harness` | Agent interfaces, independent bounded observations and headless semantic-query/verifier interfaces with deterministic tool execution. |
| `apps/web` | Shared authority controller, Svelte scene/chat workspace, exact proposal approval and inverse validation, numbered synthetic point context; disposable Three.js caches/overlays and independent Toronto inspection channels. |
| `apps/server` | Single-user local project authority and bounded `/project/*` context/proposal/approval/undo/Save/Load; read-only `/health`, Toronto metadata/observation/closest-label, shared disk index and backpressured full-resolution streams; live-authority-bound deterministic `/chat/inspect`; separate startup-bound `/cad/*` sandbox with isolated kernel worker. |
| `tests/*.test.ts` | Node checks for contracts, coordinates, bounds, rendered dimensions, raycasting and HTTP routes. |
| `scripts/browser-smoke.mjs`, `scripts/browser-toronto-smoke.mjs` | Existing-Chrome CDP checks of demo and actual Toronto preview; console/screenshot evidence. |
| `scripts/check-toronto-preview.ts` | Bounded actual-artifact observation checks, separate from full preprocessing validation. |

Dependencies flow from web/server to project-state to contracts; geometry depends on contracts; agent-harness depends on contracts and the geometry interface. Viewer and kernel types must not leak into product-agent interfaces.

## State and rendering

`ProjectState` carries geometry revision, coordinate metadata, entities and selected entity ID. TypeScript `readonly` expresses intent; it is not runtime deep freezing. Runtime assertions validate finite coordinates, positive box dimensions, unique IDs and valid selection references.

`ProjectSession` owns geometry, session/frame binding, retained exact proposals and undo history. Startup loads a strictly validated saved snapshot or starts the demo when no file exists; corrupt persistence fails explicitly. Browser `/project/session` reads and returned commit snapshots supply both viewer and chat, never a second seed. Explicit Save uses a fixed operator-controlled path and atomic rename; Load preserves saved geometry revision but rotates session, avoiding stale-proposal ABA. See [project editing guide](project-editing.md).

Entity IDs in state are authoritative. Three objects carry IDs as lookup hints; picking checks them against state. Meshes, point buffers, materials, pins and wireframe previews are disposable render caches. Selection/camera/pins preserve geometry revision and are not persisted. Exact synthetic A/B references reach deterministic `/project/context`; Toronto references remain unmapped. Approved box/inverse candidates validate parameters and preserved unrelated entities before one atomic revision increment. Snapshot replacement remounts the demo camera; runtime WebGL loss/restoration reports render status independently of committed geometry. Client generation/abort gates suppress late replies; ambiguous mutation blocks writes until explicit Refresh.

See [coordinate decision](decisions/001-coordinate-conventions.md): meters, right-handed Z-up, translation-only origin. Render local coordinates, not large world offsets. The demo contains 441 synthetic points and a `1.8 × 1.2 × 1.5 m` box centered at `[0, 0, 0.75]`. The box is a mesh proposal, **not an OpenCascade body or verified solid**.

## Read-only dataset observations

Toronto3D is separate from editable `ProjectState`. Shared `DatasetInfo`, `PointLod` and `PointObservation` contracts carry dataset artifact revision, coordinate frame/origin, stable point provenance and concrete bounded sample arrays. `PointObservationSource` in agent-harness exposes `observe(lod, signal)` without renderer, Pi or kernel types; the server's `PotreeDataset` provides the concrete prepared-file implementation. Neither viewer nor sampling changes geometry authority or a project revision.

The web uses independent sampled display, harness and display-only full-resolution crop channels with separate cancellation/settings/results. The editable local-meter crop box/frozen camera window is disposable viewer selection state, not a project entity or CAD edit. Full-resolution queries follow intersecting hierarchy proxies/all levels and test exact points against an AABB plus optional six camera-volume planes; task005 removes total point/source-work/time caps. Backpressured NDJSON batches, bounded source reads and independent progressive GPU chunks replace monolithic results; total GPU memory can still exhaust resources, with explicit incomplete/error/cancel states rather than downsampling. Harness sampling remains the existing bounded first-chunk algorithm. Display progressively replaces a root sample with the selected capped sample; harness produces downloadable observation JSON, not model calls. Vite dev and preview proxy `/datasets/`, `/project` and `/chat/` to the local server (project edits remain separately bounded). Fixed asset names, realpath/no-follow checks, numeric/range/per-read safeguards and request concurrency limits prevent arbitrary paths/raw whole-file allocations. A full-resolution selection can intentionally traverse the entire prepared cloud progressively; it is not a raw whole-file download. No raw range/file endpoint is exposed. See [preview design/run instructions](web-preview-lod.md) for exact limits, first-chunk/depth limitations and fingerprint semantics.

Toronto uses its own shared origin `[627285, 4841948, 0]` meters, never the demo origin. Local int32-scaled Potree positions are rendered in a right-handed Z-up frame. This translation-only imported observation adds no CRS conversion or geometry-edit semantics.

## Fixed-view visual observations

[Task027](tasks/027-visual-observations.md) adds explicit local capture in the synthetic and Toronto scenes. The web-owned disposable adapter emits one PNG/SHA256 bundle with drawing-buffer viewport, camera pose/projection, source revision, meter frame/origin and actual overview/detail coverage. Capture/hash races and changed view generations fail closed. Pixel coordinates refer to the captured image's top-left drawing buffer, not CSS pixels; resolution returns original point provenance, ambiguity or no-hit, with clipping and candidate-sightline mesh occlusion. Camera, resize, selection/overlay, detail/LOD, source and lifecycle changes invalidate resolution/export. Images and metadata remain observations, never geometry authority.

The observation panel previews and downloads locally; it never sends images. [Task028](tasks/028-model-visual-grounding.md) adds a separate explicit Attach scene screenshot action in chat. Results explicitly identify browser-observed provenance, not independently server-verified original records or CAD. ## Interactive agent and scene requirement

The final product harness is **not headless**. The product agent interacts with the user through both chat and the live 3D scene. User-selected points/entities, named spatial references such as A/B, and relevant scene context must be available to the agent—not only text commands or independent backend observations. Selections retain stable provenance/IDs, units, coordinate frame and source/project revisions; stale selections or unmapped dataset/project frames must be resolved explicitly rather than silently reinterpreted.

Required final workflow example: the user selects point A and point B in the scene and asks **“build a channel from point A to point B.”** The agent consumes those bound selections, asks for unresolved design parameters as needed, and presents a geometry proposal with visible scene feedback. Approval, geometric postconditions and revision-checked publication precede reporting a committed edit; the resulting geometry appears in the same authoritative scene. Scene interaction is a first-class agent input/output channel, not merely a passive viewer beside chat.

Task019 now routes explicit selections to read-only model context. This final-product requirement is not a claim that model-driven channel modeling or approved CAD publication is already implemented. Headless kernel/backend verification remains useful infrastructure and does not define the product UX.

## Real CAD sandbox

[Task013](tasks/013-cad-engine.md) implements actual OpenCascade using pinned `replicad-opencascadejs@1.1.0` direct bindings (no Replicad JS wrapper). A new `CadAdapter` accepts kernel-independent operation contracts; only geometry's `/cad-kernel` implementation imports native types. The server lazily loads that implementation in an isolated worker, not the HTTP thread or agent interfaces. [API/limits guide](cad-engine.md) covers box, Z-cylinder, immutable union/subtract/intersect, inspection, plain-array tessellation, meter STEP export and deletion.

Sandbox bodies have immutable IDs/revision1 and explicit demo session/source revision/frame provenance, local meter right-handed Z-up coordinates. They are not project entities, commits or approved edits. Exactly one nonempty positive-volume solid, native geometric/exact BRep checks, measured bounds/volume/topology and STEP meter roundtrip gate separate real solid validity from rendering. Application-specific verified edit postconditions remain future work. Task013 did not change `/project`, chat or viewer meshes; tasks014/015 now add only non-CAD box parameter publication. Sandbox bodies still do not enter that project.

One admission includes bounded body reading; no queue. Input/registry/boolean-complexity/topology/output limits and hard15s kernel timeout contain native work. Cancellation of dispatched operations, kernel-operation timeout (not body-read timeout), unexpected worker failure or server close terminates the kernel and invalidates all sandbox handles; next use starts fresh after termination. JS heap limits do not cap WASM memory; bounded native workloads are not a peak-memory/security proof. Production remains loopback-only and unauthenticated—Host/Origin checks do not authorize public hosting. Task013 baseline138/138, independent HTTP/kernel/failure probes and fresh source review pass. New untracked graph coverage and parent stale-LSP cache remain incomplete; no clean graph certification claimed. No rendering/UI changes or task013 browser check.

## Toolchain and distribution

The private pnpm 10 workspace targets Node 22 (`>=22.12.0 <23`) with TypeScript 5.9, Svelte 5, Vite 7 and Three.js. Workspace packages export TypeScript source; they are not published or independently emitted distributions.

- `pnpm dev`: web at `127.0.0.1:5173` and local server at `127.0.0.1:3001` (local project authority/editing, read-only data/inspection chat and separate CAD sandbox).
- `pnpm typecheck`: recursive checks, including `svelte-check`.
- `pnpm test`: `tsx --test tests/*.test.ts`.
- `pnpm build`: Vite web distribution in `apps/web/dist`; server `build` is `tsc --noEmit`, not an emitted server package. Library packages have no build scripts.
- `pnpm verify`: typecheck, test, build in sequence; explicitly reminds that browser checks are separate.
- `pnpm verify:browser [CDP endpoint]`: starts a built-preview server and checks an existing Chrome; no browser download or launch.
- Browser verification needs a functioning browser harness and CDP-enabled Chrome; a script declaration alone is not evidence of a completed check.
