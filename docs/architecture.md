## State and rendering

`ProjectState` carries geometry revision, coordinate metadata, entities and selected entity ID. TypeScript `readonly` expresses intent; it is not runtime deep freezing. Runtime assertions validate finite coordinates, positive box dimensions, unique IDs and valid selection references.

`ProjectSession` owns geometry, session/frame binding, retained exact proposals and undo history. Startup loads a strictly validated saved snapshot or starts the demo when no file exists; corrupt persistence fails explicitly. Browser `/project/session` reads and returned commit snapshots supply both viewer and chat, never a second seed. Explicit Save uses a fixed operator-controlled path and atomic rename; Load preserves saved geometry revision but rotates session, avoiding stale-proposal ABA. See [project editing guide](project-editing.md).

Entity IDs in state are authoritative. Three objects carry IDs as lookup hints; picking checks them against state. Meshes, point buffers, materials, pins and wireframe previews are disposable render caches. Selection/camera/pins preserve geometry revision and are not persisted. Exact synthetic A/B references reach deterministic `/project/context`; Toronto references remain unmapped. Approved box/inverse candidates validate parameters and preserved unrelated entities before one atomic revision increment. Snapshot replacement remounts the demo camera; runtime WebGL loss/restoration reports render status independently of committed geometry. Client generation/abort gates suppress late replies; ambiguous mutation blocks writes until explicit Refresh.

See [coordinate decision](decisions/001-coordinate-conventions.md): meters, right-handed Z-up, translation-only origin. Render local coordinates, not large world offsets. The demo contains 441 synthetic points and a `1.8 × 1.2 × 1.5 m` box centered at `[0, 0, 0.75]`. The box is a mesh proposal, **not an OpenCascade body or verified solid**.

## Interactive agent and scene requirement

The final product harness is **not headless**. The product agent interacts with the user through both chat and the live 3D scene. User-selected points/entities, named spatial references such as A/B, and relevant scene context must be available to the agent—not only text commands or independent backend observations. Selections retain stable provenance/IDs, units, coordinate frame and source/project revisions; stale selections or unmapped dataset/project frames must be resolved explicitly rather than silently reinterpreted.

Required final workflow example: the user selects point A and point B in the scene and asks **“build a channel from point A to point B.”** The agent consumes those bound selections, asks for unresolved design parameters as needed, and presents a geometry proposal with visible scene feedback. Approval, geometric postconditions and revision-checked publication precede reporting a committed edit; the resulting geometry appears in the same authoritative scene. Scene interaction is a first-class agent input/output channel, not merely a passive viewer beside chat.

Task019 now routes explicit selections to read-only model context. Model-driven channel modeling remains future work; task034 supplies only the bounded Toronto box/cylinder publication path. Headless kernel/backend verification remains useful infrastructure and does not define the product UX.
